Framework-Only vs Deep Developer

The same bug. Two completely different ways of thinking.

👨‍💻 Framework-Only

  • ▸ Is the right React hook used?
  • ▸ Look at the component code
  • ▸ Maybe try another state library
  • ▸ Restart the dev server

🛠️ Platform-Aware

  • ▸ HTTP request headers — is caching enabled?
  • ▸ Is the API returning fresh data?
  • ▸ Is the frontend caching the response?
  • ▸ Browser cache / Service Worker
  • ▸ API response headers (ETag, Cache-Control)
  • ▸ Is frontend data stored correctly?

Why this distinction matters

Frameworks are incredible productivity tools. They let us ship features fast. But when things break in production — stale data, unexpected cache hits, hydration mismatches, or silent 304s — the answer is almost never "wrong hook".

The network tab, the Application tab, response headers, and understanding the full request lifecycle separate junior framework users from senior engineers who can actually diagnose real-world issues.

When the framework leaks

Abstractions are useful until they aren’t. Every framework eventually leaks — the moment the nice API can’t hide the underlying system anymore. Depth is what lets you fix the leak instead of waiting for a library patch or a migration guide.

Silent 304 / stale data

The UI shows old content. React state looks fine. The real culprit is a Cache-Control or ETag response the framework never surfaces.

Depth: read response headers, not just JSON

React StrictMode double effects

Effects fire twice in development. A framework-only view blames “weird React.” Depth knows it’s intentional — and that production won’t double-invoke.

Depth: understand the render lifecycle

N+1 queries via the ORM

The page is slow. The ORM “just works” until lazy loading triggers dozens of queries. The abstraction hid the cost until traffic hit.

Depth: inspect the actual SQL / network waterfall

Service Worker / Cache Storage

Users see a broken or outdated UI after a deploy. The framework’s data layer is fine — a Service Worker is serving a previous build.

Depth: Application tab → Cache Storage / SW

Hydration mismatch

Server HTML doesn’t match the client’s first render. The error message is opaque if you only know component props and not the SSR contract.

Depth: know what the server actually sent

CSS specificity / cascade fights

Utility classes or CSS-in-JS suddenly “don’t apply.” The framework’s styling layer is fighting the cascade or load order.

Depth: inspect computed styles, not just class names

Interactive debugging checklist

When data looks wrong, work through these steps. Progress is saved in this browser.

0 / 7
  • Open DevTools → Network. Hard refresh (Cmd/Ctrl+Shift+R) Bypass browser cache so you see real requests
  • Inspect the request: status code, request headers, response headers Look for 200, 304, 404, or unexpected redirects
  • Check Cache-Control, ETag, Age, X-Cache These headers reveal caching layers (browser, CDN, edge)
  • Disable cache in Network tab and retry Confirm the problem disappears when cache is forced off
  • Check Application tab: LocalStorage, IndexedDB, Cache Storage, Service Workers Stale client-side data is a very common culprit
  • Confirm the API itself returns the expected fresh payload Hit the endpoint directly or via a tool that bypasses the frontend
  • Only then dig into React state, effects, and hooks Framework issues come last — after the platform is verified
🎉 All steps checked — you investigated the full stack. Nice work!

Abstraction leak checklist

Can you recognize these leaks when they show up? Check each one off as you internalize it.

0 / 6
  • Stale UI + healthy React state → check response headers first 304 / Cache-Control / ETag often explain “impossible” data
  • Double effect in dev is often StrictMode, not a bug Production will not double-invoke the same way
  • Slow page + ORM → look for N+1 in the network / SQL waterfall Lazy loading hides cost until load increases
  • Broken UI after deploy → check Service Worker & Cache Storage Old assets can outlive your new release
  • Hydration error → compare server HTML to first client render The mismatch is in the SSR contract, not just props
  • Styles “not applying” → inspect computed styles & cascade Framework class names can still lose the specificity fight
🎉 You can spot the common leaks. That’s depth in action.

Remove the Framework drill

A practical way to build depth: take something the framework does for you, strip it back to the platform, then put the framework back on with clearer eyes.

1

Pick a small feature

Choose something you recently built with the framework — a filtered list, a form submit, a client-side route, or a data fetch with loading/error states.

2

Rewrite it in vanilla JS (or minimal platform APIs)

No React, no router, no data library. Use fetch, DOM APIs, history.pushState, and plain event listeners. Notice what you have to handle yourself.

3

List what the framework was doing

Diff the two versions mentally: re-renders, dependency tracking, cache keys, cancellation, error boundaries, routing sync. Write the list down — that’s the abstraction surface.

4

Put the framework back — on purpose

Re-implement with the framework, but only after you can explain each piece it owns. You’ll debug faster the next time one of those pieces leaks.
