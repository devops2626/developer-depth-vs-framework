Framework-Only vs Deep Developer

The same bug. Two completely different ways of thinking.

👨‍💻 Framework-Only

  • ▸ Is the right React hook used?
  • ▸ Look at the component code
  • ▸ Maybe try another state library
  • ▸ Restart the dev server

🛠️ Platform-Aware

  • ▸ HTTP request headers — is caching enabled?
  • ▸ Is the API returning fresh data?
  • ▸ Is the frontend caching the response?
  • ▸ Browser cache / Service Worker
  • ▸ API response headers (ETag, Cache-Control)
  • ▸ Is frontend data stored correctly?

Why this distinction matters

Frameworks are incredible productivity tools. They let us ship features fast. But when things break in production — stale data, unexpected cache hits, hydration mismatches, or silent 304s — the answer is almost never "wrong hook".

The network tab, the Application tab, response headers, and understanding the full request lifecycle separate junior framework users from senior engineers who can actually diagnose real-world issues.

Interactive debugging checklist

When data looks wrong, work through these steps. Your progress is saved in this browser.

0 / 7
  • Open DevTools → Network. Hard refresh (Cmd/Ctrl+Shift+R) Bypass browser cache so you see real requests
  • Inspect the request: status code, request headers, response headers Look for 200, 304, 404, or unexpected redirects
  • Check Cache-Control, ETag, Age, X-Cache These headers reveal caching layers (browser, CDN, edge)
  • Disable cache in Network tab and retry Confirm the problem disappears when cache is forced off
  • Check Application tab: LocalStorage, IndexedDB, Cache Storage, Service Workers Stale client-side data is a very common culprit
  • Confirm the API itself returns the expected fresh payload Hit the endpoint directly or via a tool that bypasses the frontend
  • Only then dig into React state, effects, and hooks Framework issues come last — after the platform is verified
🎉 All steps checked — you investigated the full stack. Nice work!
